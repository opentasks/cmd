# Semantic ID System with Global Sequential Numbering

## Design Decision

Task IDs are simple global sequential numbers. Type information is stored in frontmatter, not in the ID. Storage backend (MarkdownFileStorage) organizes files by epic hierarchy with human-readable directory and file names.

## ID Format

- **Format**: Simple integer (1, 2, 42, 1000)
- **Scope**: Global across entire project
- **Generation**: Count all task files in project, next ID = count + 1
- **No type prefix**: Type is metadata in frontmatter only
- **No collision handling needed**: Global counter guarantees uniqueness

## Type Mapping (for reference)

| Type      | Code |
|-----------|------|
| epic      | e    |
| plan      | p    |
| research  | r    |
| story     | s    |
| decision  | d    |
| task      | t    |

## ID Generation Strategy

1. **Walk project directory**: Find all `.md` files recursively
2. **Parse frontmatter**: Extract ID from each task file
3. **Find maximum ID**: Track the highest ID seen
4. **Return max + 1**: New task gets `max_id + 1` as its ID
5. **No reuse**: Even if tasks are deleted, IDs are never reused

```go
// Pseudocode
func NextID(projectPath string) int {
    var maxID int
    
    // Walk all files, find the maximum ID from frontmatter
    filepath.Walk(projectPath, func(path string, info os.FileInfo, err error) error {
        if !strings.HasSuffix(path, ".md") {
            return nil
        }
        
        task, err := parseTaskFile(path)
        if err != nil {
            return nil  // Skip unparseable files
        }
        
        if task.ID > maxID {
            maxID = task.ID
        }
        return nil
    })
    
    return maxID + 1
}
```

## File Naming Convention (MarkdownFileStorage Detail)

This is a storage backend implementation detail. The directory and filename structure is:

```
<epic_id>-<epic_slug>/<typecode>-<id>-<slug>.md
```

**Components**:
- `epic_id`: ID of parent epic (or 0 for root-level epics)
- `epic_slug`: Slugified summary of epic title
- `typecode`: Single letter (e, p, r, s, d, t)
- `id`: Task ID number
- `slug`: Slugified summary of task title

**Examples**:
- `1-design-opentasks/p-3-design-roadmap.md` (task 3, plan, under epic 1)
- `1-design-opentasks/s-5-task-data-model.md` (task 5, story, under epic 1)
- `e-1-design-opentasks.md` (task 1, epic, at root level)
- `2-implement-core/s-11-build-storage-layer.md` (task 11, story, under epic 2)

## Implementation Notes

- **ID is source of truth**: Stored in YAML frontmatter (`id: 42`)
- **Filename is storage detail**: Different backends can organize files differently
- **No type in ID**: Type determined by `type: story` in frontmatter
- **Epic hierarchy in filesystem**: Directory names reflect epic structure for discoverability
- **Human-readable paths**: Directory and file slugs make browsing easier

**Key points**:
- Only epics at root level (`e-{id}-{slug}.md`)
- Epic directories named `{id}-{slug}/` (id + 3-5 word slug)

- Slug examples: `design-roadmap`, `evaluate-storage-options`, `task-data-model`

## Why This Design

1. **Simplicity**: No type-specific counters, no collision logic
2. **Decoupling**: ID system is independent from storage format
3. **Flexibility**: Different storage backends can organize files differently
4. **Discoverability**: Human-readable directories and filenames (ID + 3-5 word slug)
5. **No state management**: Filesystem is the source of truth
6. **Sortability**: Filenames sort naturally by type code then ID
7. **No ID reuse**: Finding max ID ensures deleted tasks don't cause collisions
8. **Self-healing**: Works correctly even if files are manually created/edited
