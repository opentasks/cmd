# Project Structure and Directory Layout

Complete specification of how OpenTasks projects are organized on disk and how project discovery works.

## Project Directory Structure

### Default Layout (local .tasks)

```
my-git-repo/
├── .tasks/                                  # Project root directory
│   ├── config.toml                          # Project configuration
│   ├── e-1-design-opentasks.md              # Only epics at root level
│   ├── e-2-implement-core.md
│   ├── 1-design-opentasks/                  # Epic 1 subdirectory (ID + slug)
│   │   ├── p-3-design-roadmap.md            # All child tasks grouped here
│   │   ├── r-4-evaluate-storage.md
│   │   ├── s-5-task-data-model.md
│   │   └── s-6-semantic-id-system.md
│   ├── 2-implement-core/                    # Epic 2 subdirectory (ID + slug)
│   │   ├── s-11-build-storage-layer.md
│   │   ├── s-12-implement-query.md
│   │   └── t-13-write-unit-tests.md
│   └── templates/                           # Optional local templates
│       ├── epic.md
│       ├── plan.md
│       └── story.md
└── ... (other project files)
```

**Root-level constraint**: Only epics are stored at the root level. All other tasks (plans, research, stories, decisions, tasks) must have a parent epic and live in the corresponding epic subdirectory. This ensures clear hierarchy and organization.

### XDG Layout (user data directory)

```
${XDG_DATA_HOME}/opentasks/
├── config.toml                              # Global user configuration
├── templates/                               # User-level templates (fallback for all projects)
│   ├── epic.md
│   ├── plan.md
│   ├── research.md
│   ├── story.md
│   ├── decision.md
│   └── task.md
└── projects/                                # User's projects
    ├── github_com-user-opentasks/
    │   ├── config.toml                      # Project-level config
    │   ├── e-1-design-opentasks.md
    │   ├── 1-design-opentasks/
    │   │   ├── p-3-design-roadmap.md
    │   │   └── ...
    │   └── ...
    └── other-project-id/
        ├── config.toml
        └── ...
```

**Default XDG_DATA_HOME**: `$HOME/.local/share` (Linux), `$HOME/Library/Application Support` (macOS)

### Custom Path Layout

```
/my/custom/tasks/path/
├── config.toml                              # Project config
├── e-1-design-opentasks.md
├── 1-design-opentasks/
│   ├── p-3-design-roadmap.md
│   └── ...
└── 2-implement-core/
    ├── s-11-build-storage.md
    └── ...
```

## File Naming Convention (MarkdownFileStorage)

This is a storage backend implementation detail. Files are organized hierarchically by epic.

**Pattern**: `<epic_id>-<epic_slug>/<typecode>-<id>-<slug>.md`

**Components**:
- `epic_id`: ID of parent epic (omitted for root-level epics)
- `epic_slug`: Slugified summary of epic title (3-5 key words, see below)
- `typecode`: Single letter (e, p, r, s, d, t)
- `id`: Task ID number (global sequential)
- `slug`: Slugified summary of task title (3-5 key words, see below)
- Extension: Always `.md` (markdown)

## Slug Generation

Slugs are human-readable summaries in the filename for discoverability.

**Strategy**: Keep first 3-5 key words or ~50-60 characters, whichever is shorter

**Examples**:
- "Task Data Model and Relationships" → `task-data-model` (3 words)
- "Semantic ID System with Collision Detection" → `semantic-id-system` (3 words)
- "BaseStorage Interface and Responsibilities" → `base-storage-interface` (3 words)
- "Design OpenTasks Core System" → `design-opentasks-core` (4 words, under 60 chars)

**Implementation**:
1. Convert to lowercase
2. Remove articles (a, an, the) and conjunctions (and, or, with, for)
3. Keep first N words until approaching 60 chars
4. Join with hyphens
5. Remove special characters

**Note**: Slug is informational only - the ID in frontmatter is the source of truth. Stale slugs (from title changes) are acceptable.

**Examples**:
```
e-1-design-opentasks.md                     # Epic 1, root level
e-2-implement-core.md                       # Epic 2, root level
1-design-opentasks/p-3-design-roadmap.md    # Task 3 (plan), under epic 1
1-design-opentasks/r-4-evaluate-storage.md  # Task 4 (research), under epic 1
1-design-opentasks/s-5-task-data-model.md   # Task 5 (story), under epic 1
2-implement-core/s-11-build-storage.md      # Task 11 (story), under epic 2
```

**Key insight**: Filename is storage detail. The ID in frontmatter (`id: 42`) is the source of truth.

## ID System

**Global Sequential Numbers**:
- Format: Simple integer (1, 2, 3, ..., 42, ..., 1000)
- Scope: Global across entire project
- Generation: Count all `.md` files, next ID = count + 1
- Type: Stored in frontmatter (`type: story`), not in ID

**Frontmatter Example**:
```yaml
id: 5
type: story
title: Implement task data model
status: todo
relationships:
  - type: parent
    taskID: 1
```

## config.toml Location Hierarchy

When loading a project, the system looks for config in this order:

1. **Explicit**: Path specified via CLI flag `--path` or env var `OPENTASKS_PROJECT_PATH`
2. **Local**: `{project-root}/config.toml`
3. **XDG**: `${XDG_DATA_HOME}/opentasks/config.toml` (global defaults)

Config files are cumulative:
- Global config provides user-wide defaults
- Project config overrides global for that project
- CLI flags override both

## Project Discovery

### Explicit Project Path

```bash
# All of these point to the same project
opentasks --path /my/project/tasks
OPENTASKS_PROJECT_PATH=/my/project/tasks opentasks
opentasks  # If config.toml specifies path
```

### Implicit Project Paths

When no explicit path is given:

1. Check current directory for `.tasks/` → use it if found
2. Check parent directories recursively for `.tasks/` (up to home or root)
3. Check `${XDG_DATA_HOME}/opentasks/projects/{derived-id}/` for git-based projects
4. If config.strict=true: Error if not found
5. If config.strict=false: Create at highest precedence location (usually `${XDG_DATA_HOME}/...`)

### Git-Based Project ID Derivation

For projects inside git repositories, derive a stable project ID from the repo URL:

```go
// Example: https://github.com/user/opentasks.git
// Derived ID: github_com-user-opentasks

// Example: git@github.com:user/opentasks.git
// Derived ID: github_com-user-opentasks

// Example: /path/to/local/repo/.git
// Derived ID: (based on dir name + some hash)

Algorithm:
1. Read .git/config (for remote URL or use directory name)
2. Normalize URL (remove protocol, .git suffix)
3. Replace special chars with underscores
4. Use as subdirectory in ${XDG_DATA_HOME}/opentasks/projects/
```

## Template Search Path

When creating a new task of type "story", templates are resolved in this order:

1. **Config-specified**: `config.toml#templates.story` (absolute or relative path)
2. **Project-local**: `{project-root}/templates/story.md`
3. **User-level**: `${XDG_DATA_HOME}/opentasks/templates/story.md`
4. **Built-in**: Hard-coded Go embedded templates

If a path doesn't exist, fall through to the next. If all fail, return error.

## Config File Examples

### Minimal config.toml (uses all defaults)

```toml
[project]
name = "My Project"
```

### Full config.toml

```toml
[project]
name = "Complex Project"
description = "A project with custom workflow"
owner = "team-backend"

[workflow]
statuses = ["backlog", "todo", "in-progress", "review", "done", "archived"]
initial = "backlog"

[[workflow.transitions]]
from = "backlog"
to = ["todo", "archived"]

[[workflow.transitions]]
from = "todo"
to = ["in-progress", "backlog", "archived"]

[[workflow.transitions]]
from = "in-progress"
to = ["review", "todo", "archived"]

[[workflow.transitions]]
from = "review"
to = ["done", "in-progress", "archived"]

[[workflow.transitions]]
from = "done"
to = ["archived"]

[templates]
epic = "./templates/epic.md"
plan = "./templates/plan.md"
research = "./templates/research.md"
story = "./templates/story.md"
decision = "./templates/decision.md"
task = "./templates/task.md"

[storage]
backend = "markdown-fs"
path = "./tasks"
```

## Multi-Project Management

The system supports working with multiple projects:

```bash
# Work with project A
opentasks --path /path/to/project-a task ls

# Work with project B
opentasks --path /path/to/project-b task ls

# List tasks from both (handled by higher-level tools)
opentasks-query-all-projects --filter "status:in-progress"
```

Each BaseStorage instance is scoped to one project via its initialization config.

## Strict vs. Lenient Mode

**Strict mode** (`config.strict = true`):
- Fails if project not found at specified path
- Fails if config references missing templates
- Validates all relationships point to existing tasks

**Lenient mode** (default):
- Creates project if not found
- Falls back to built-in templates if missing
- Allows forward references (relationships to tasks not yet created)
